# Changelog

All notable repository changes are recorded here, including small fixes, documentation-only edits, configuration changes, tests and repository-governance changes. Entries describe repository facts and do not imply that planned application capabilities have been implemented.

The repository policy in `CLAUDE.md` requires every change, however small, to have a corresponding entry in this file **in the same commit**. This includes changes to `CLAUDE.md` and to this changelog.

## [Unreleased]

### Fixed
- **2026-11-15 — Restricted Holiday classification removed from the draft contract:** Corrected a contradiction with requirements §4.1, which makes a Restricted Holiday an ordinary working day and requires its dates and names to be ignored entirely. The draft-register contract introduced in the previous commit offered `CalendarDayKind.RESTRICTED_HOLIDAY` and treated it as a non-working classification, so a caller could have marked a date non-working for a reason the requirement says must never affect the calendar. The member is removed rather than aliased to `WORKING`, because an alias would still accept Restricted Holiday data and let a caller believe it had been classified. A date that is only a Restricted Holiday is now classified `WORKING`; a date that is both a Restricted Holiday and a Sunday keeps only the Sunday classification and reason, with no Restricted Holiday information attached. The requirement's other instruction, that a Restricted Holiday coinciding with an independently approved non-working condition preserves that condition, needed no code change because that behaviour never depended on the removed member. No import, table, column, display field or generated description carries Restricted Holiday data. Added four tests pinning the absence of the member, the working classification of a Restricted Holiday-only date, the Sunday-only classification of an overlapping date, and the absence of the word from every projected reason. The requirements baseline states the correction in §4.1 terms and §19 no longer implies restricted holidays are a non-working class. The full suite is 333 tests, all passing. No allocator, validator or scheduling behaviour changed.

### Added
- **2026-11-15 — Draft-register generation from allocator decisions:** Added `dailyworkreg/application/`, the first layer above the domain, which turns a typed request into a draft register for the selected months. It consumes `run_cycle()` and `run_fallback()` and presents what they decided; it computes no DTC target, distributes no cycle, evaluates no revisit interval, counts no capacity, overrides no monthly maximum, moves no visit, adds no filler visit, relaxes no obligation and treats no weight as an obligation. A month's projected visits are asserted equal to the allocator's own visits rather than inspected for plausibility. Coverage-cycle generation requires the declared cycle and rejects the fallback-only inputs (`dtc_target`, `area_required`, `feeder_required`) instead of accepting them as silent no-ops that `run_cycle()` would ignore, and capacity-fallback generation rejects a declared cycle, so neither mode can be half-applied. Commitments are passed to the allocator unchanged, including those in cycle months that are not being generated; a committed visit outside the selection is still checked against the real calendar, so calendar metadata for the dates those commitments sit on is required and its absence is reported under `commitment_date_metadata_missing` with the date that is missing rather than surfacing later as a spurious violation. Every selected date produces exactly one ordered row, including Sundays, second and fourth Saturdays, holidays, leave and other non-working dates, with the classification and its English and Kannada reasons supplied by the caller: the layer imports no holiday data, infers no weekly off and invents no name, and missing, duplicate or contradictory date metadata and missing, unknown or duplicate display metadata are rejected. Visits carry the allocator's stable asset id and separate display names, so no display string becomes a source of truth. Each month keeps its own outcome: feasible months are allocation-complete, infeasible months keep their structured evidence, and a month whose bounded search ended without a verdict is reported unresolved and never as feasible, infeasible, an error or an empty completed month, with its committed visits retained. Fixed and newly allocated visits are distinguishable by provenance taken from the allocator's own `fixed` input. Over-coverage is projected as a resolved exception carrying the asset, the declared obligation and the actual committed count, and no commitment is deleted to make the arithmetic work. A commit against the earlier constraint-inventory defect: an unschedulable month returns its commitments only in `fixed`, so the projection reads both fields; reading only the new visits erased every locked visit from exactly the month where losing them matters most, and a test now pins it. Only complete calendar months are generated, under `partial_month_selection_unsupported`, because the proration rounding rule remains undeclared and the range is never silently widened. The result carries a snapshot of the allocator and generator versions, mode, seed, range, months, rotation offset, attempt budget, the declared cycle with its resolution, prior history and inventoried commitments, plus canonical content fingerprints of the roster, configuration, calendar and display metadata. It also names the masters still absent, so allocation success cannot be read as a finished operational diary. Activity and event entries supplied by the caller are projected onto their rows and consume no field-visit capacity; no activity catalogue, holiday baseline, DTC roster import, recurring rule or Kannada translation was added. Recorded as §19 of the requirements baseline. The overall outcome reuses the allocator's own worst-month precedence rather than recomputing it, so a proof of infeasibility outranks an unsettled month and no second ordering of the same three outcomes exists. Added `tests/test_draft_generation.py` with 54 tests covering mode integration, exact projection, provenance, row-per-date completeness and ordering, outcome preservation for all three verdicts, over-coverage and rejected commitments, every input boundary and reproducibility. The full suite is 329 tests, all passing, with the 274 domain tests retained; the validator soundness harness and the allocator harness both still hold. No FastAPI route, SQLite schema, persistence, UI, PDF or Excel output, review, finalisation, correction revision or backup and restore was added.

### Changed
- **2026-11-15 — An invalid-commitment error now carries its structured violations:** `InputError` gains an optional `violations` tuple, defaulting to empty, and `run_cycle()` populates it when it raises `cycle_fixed_visit_invalid`. A caller that must show which commitment was refused, on which date and under which constraint previously had only a human-readable message to work from, and the documented rule is that no caller parses message text. The field is additive, so every existing raise site and every existing caller is unaffected and the error's own message, constraint identifier and `asset_id` are unchanged. Added one test to `tests/test_cycle_commitments.py` pinning that the error carries the violation, its constraint, its asset and the offending date. This is preparation for the draft-register generation layer, which has to report a rejected commitment as data rather than as prose. No scheduling decision, feasibility verdict, cycle resolution or policy changed; no allocator behaviour was touched.

### Fixed
- **2026-11-15 — Cycle obligations, verification, reconciliation and seed effectiveness corrected:** Fixed six defects in the joint target allocator found in review, without changing the settled scheduling policy. Cycle obligations now carry integer visit counts per asset: the resolver previously built a month's obligations from a set of asset ids, so a DTC owing two visits in one month was recorded as owing one while the month total said two, and four visits were silently reduced to one rather than reported as over the monthly maximum. `verify_cycle()` is now an independent structural verifier rather than a key counter: it checks month identity and ordering against the declared cycle, month indices, roster membership, positive integer obligation values, per-month totals against their obligation sums, per-asset totals against both `cycle_totals` and `visits_per_asset`, scheduled assignments against obligations including multiplicity, and the even-distribution contract; `run_cycle()` verifies a resolution before allocating from it and fails closed under `cycle_resolution_invalid` rather than proceeding. Committed visits are now reconciled across the whole cycle: a fixed visit in any month discharges that asset's cycle obligation even when the resolver assigned a different month, so the asset is no longer allocated a second visit; commitments in months that are not selected for placement, and in months whose allocation fails, are still carried forward as history rather than forgotten; committed visits are preserved unchanged and never duplicated; and commitments exceeding the cycle obligation are reported as `cycle_obligation_over_covered` evidence instead of fabricating or silently dropping visits. The allocation seed is now effective: the asset id was the final tie-breaker, so every seed produced the same schedule, and the earlier test compared only per-asset counts, which could never differ. Placement now derives per-asset and per-date tie keys from the seeded generator and ranks assets by constraint pressure, then remaining count, then scheduling weight, then that key, so alternative seeds reach different valid arrangements while per-asset counts stay fixed. The seed still cannot outrank constraint pressure or change an obligation. Scheduling weights are passed into the allocator through `AllocationRequest.weights`, so the weight model is computed once by `DtcWeights` instead of being re-derived, and a missing weight sorts last. An explicitly empty, duplicated or out-of-cycle month selection is now rejected with `InputError` under stable identifiers rather than producing a successful-looking empty result, which previously reported the worst of no months, that is success, from a run that placed nothing; month selections and fallback sequences are processed chronologically so history is never carried backwards. Partial months fail closed in the allocator itself: `allocate_month()` resolves effective limits through the proration contract first, so a partial period without explicit limits raises `InputError` rather than silently applying full-month limits, effective limits must account for the default limits explicitly (falling back to the un-prorated configured default is rejected under `partial_month_effective_limits_incomplete`), and the original and effective configurations are kept separate. The multi-month cycle and fallback helpers now state that they support full calendar months only and reject a partial period under `partial_period_unsupported`, rather than implying arbitrary date-range support. The integer rounding rule for a prorated partial month remains undeclared and therefore still unresolved. Added `tests/test_cycle_correctness.py` with 69 tests pinning each defect, including the four-visits-against-maximum-three case resolving to `INFEASIBLE` rather than a reduced obligation, tampering detection for the verifier, cycle-wide reconciliation cases, and alternative-seed schedules that are revalidated independently. The full suite is 241 tests, all passing, with the 172 pre-existing tests unmodified; the allocator harness was extended with multiplicity, verification, reconciliation and selection checks and still holds at synthetic scale. Corrected the previously recorded test count for `tests/test_allocator.py` from 28 to 27. No draft-register generation, FastAPI route, schema, database, UI, PDF or Excel output was added and no scheduling or solver dependency was introduced.

### Fixed
- **2026-11-15 — Cycle-wide commitment reconciliation made independent of month order:** Fixed the remaining cycle-wide fixed-visit defect in the joint allocator. `run_cycle()` counted committed visits across the cycle for over-coverage reporting but discharged obligations only as its chronological loop reached each commitment, starting from an empty tally. A commitment in a month the loop had not reached yet was therefore invisible while an earlier month was placed. Measured: a DTC owing one visit in a three-month cycle, with the resolver assigning that visit to November and a committed visit locked in December, produced **two** visits for an asset owing one and reported no over-coverage, because the over-coverage calculation counted commitments but not generated visits. The same blindness affected the revisit gap: the November allocation could take a date within seven days of a December commitment, December then failed to place, and the cycle was reported infeasible even when another valid November date existed. Measured on a two-visit cycle with a commitment on 2 December: November accepted 30 November, December was rejected, and the cycle came out infeasible; it now places November on 2 November and the cycle is feasible. Fixed visits are now inventoried and reconciled against the whole declared cycle before any month is allocated. Each committed DTC visit consumes exactly one obligation unit — charged to the month it falls in when that month still owes a unit, otherwise to the earliest month that does — so newly allocated visits plus committed visits equal the declared obligation for every DTC, and a whole-cycle commitment count is never subtracted independently from each month, which would over-subtract an asset owing units in two months. Every committed visit outside the month being placed is supplied to the validator as a new third input category, gap blockers, which constrain the seven-calendar-day interval in both directions while consuming no capacity and no obligation in that month; a commitment is never supplied as both the month's fixed visit and a blocker, so it is never counted twice, and the allocator does not duplicate the validator's gap arithmetic. Commitments are validated wherever they fall, including months that are not selected for placement, through a new `validate_committed_visits()` that reuses the same hard-constraint path per calendar month rather than reimplementing it; a mapping for a month outside the cycle, a visit filed under a month that does not contain its date, and a commitment failing the hard constraints all raise `InputError` under stable identifiers instead of being silently accepted as a discharge. This immediately caught a defect in this repository's own test data, which had used a Saturday as a working date in an unselected month. Cycle accounting is restricted to DTC cycle members: committed area and feeder visits are preserved, consume combined and area daily capacity and constrain gaps, but are never compared with the cycle's per-visit obligation and never produce DTC over-coverage evidence. The declared `CycleResolution` is now distinguished from the effective obligations a month is allocated against (`MonthPlan.declared_obligations` versus `MonthPlan.obligations`), and the inventoried commitments are reported on `MultiMonthResult.committed_visits`. Added `tests/test_cycle_commitments.py` with 33 tests covering the duplicate-visit defect, the future-gap constraint, a different earlier date being chosen, commitments in unselected months, over-coverage preservation, area and feeder exclusion from cycle accounting, and every rejection path. The full suite is 274 tests, all passing, with all 241 preceding tests retained; the allocator harness gained a future-commitment section and the validator soundness harness is unchanged. No tri-state semantics were weakened, no unresolved case was converted into an infeasibility claim, and no scheduling or solver dependency was introduced. No draft-register generation, FastAPI route, schema, database, UI, PDF or Excel output was added.

### Added
- **2026-11-15 — Weighted-fair targeting, no-cycle fallback and multi-month execution:** Added `dailyworkreg/domain/targeting.py`, which runs the allocator in cycle mode, in the no-cycle fallback mode, and across multiple months. Cycle mode places a declared coverage cycle month by month and carries earlier months' visits forward as history, so the seven-day interval and the fairness rotation survive the month and cycle boundary instead of resetting at it; every month of a cycle is resolved even when only some months are asked to be placed, so the cycle's obligations stay stable. The no-cycle fallback computes a capacity-bounded DTC target selected by least-recently-visited, then weight, then asset id, rotated deterministically between months, and is labelled a capacity-based monthly suggestion because without a declared cycle there is no coverage commitment; it is integrated with the month's area and feeder obligations in one joint allocation. A weighted decision never exceeds a per-asset maximum, breaks the seven-day gap or exceeds daily capacity. Corrected the cycle distribution to deal units round-robin across the cycle's months: the earlier front-loaded dealing stacked a small roster into the first months, so one DTC owing one visit over three months came out as 1/0/0 and was never revisited through the cycle, whereas owing three visits now spreads as 1/1/1. A `MultiMonthResult` reports the worst month's outcome rather than a merged success, and retains each month's own validation evidence. Recorded the implemented contract as §18 of the requirements baseline and marked §16 item 1 partially satisfied, stating plainly that the allocator is validated empirically and that no global optimality or search-completeness proof is claimed. No FastAPI route, schema, UI, PDF/Excel output, register rendering, holiday data, DTC source import or solver dependency was added.
- **2026-11-15 — Joint date-level allocator with validator-backed acceptance:** Added `dailyworkreg/domain/allocator.py`, which places a month's obligations onto eligible dates jointly across areas, DTCs and feeders. It decides only *when* each visit happens: obligations come from the validator's own resolution, and every candidate schedule is accepted or rejected by `validate_schedule(..., ValidationMode.OBLIGATIONS)`, so there is no second implementation of daily capacities, monthly maxima, working-date eligibility, asset activity or revisit gaps. Placement is constrained-first — at each step the asset with the fewest still-viable dates is placed next — so a flexible visit cannot consume the last date a tightly constrained asset needed, which is the failure mode plain first-fit suffers. Visits are spread by preferring the least-loaded then earliest viable date. Fixed visits are preserved unchanged, discharge their obligation, consume combined and area capacity and constrain new placements through the revisit gap; the remaining work per asset is the obligation minus what commitments already discharged, so a commitment is never double-counted. The tri-state contract is preserved: `FEASIBLE` is returned only after the returned witness has itself passed obligation-aware validation, `INFEASIBLE` only on the validator's own proof or an invalid commitment, and `INDETERMINATE` when the attempt budget is exhausted without proof, reported under `allocation_search_budget_exhausted` and never converted into a claim of impossibility. Construction runs before the feasibility assessment deliberately: the exact assessment spent about 40 seconds of node budget on a 54-asset month while construction found a valid month in 0.03 seconds, so the assessment is used as an infeasibility oracle and witness source only after construction fails. Malformed obligations still raise `InputError` rather than becoming a verdict. Added `tests/test_allocator.py` with 28 tests, each revalidating every successful result independently through the obligation-aware validator. No FastAPI route, schema, UI, PDF/Excel output, register rendering, holiday data, DTC source import or solver dependency was added.
- **2026-11-15 — DTC coverage-cycle resolution and monthly period limits:** Added `dailyworkreg/domain/cycle.py`, which resolves a declared DTC coverage cycle into stable per-month obligations before assessment, because the validator assesses exactly one calendar month at a time. The recorded reference case of 113 active DTCs owing one visit each over three months resolves to 38, 38 and 37 with every DTC appearing exactly once across the cycle; this follows from the general distribution rule rather than being special-cased, and a parametric test covers other counts and durations. Obligation and priority are kept strictly apart: a cycle gives every active DTC an equal obligation, and DTC weights (`kVA * class_multiplier * individual_adjustment`, DEPT 1.00 and SELF_DTC 0.20 by default) influence only the order in which scarce months are granted, never the number of visits owed. A fairness rotation orders assets by fewest prior visits, earliest last visit, heaviest weight and then asset id, with a deterministic offset so consecutive cycles do not always favour the same ids. The DEPT/SELF_DTC split is modelled as separate DTC metadata rather than as extra `AssetType` members, because that enum decides which visits share the daily capacities and extending it would change capacity accounting. Added `verify_cycle()` so a stored plan can be checked without re-running resolution. Added `dailyworkreg/domain/prorating.py`, which applies a partial month's effective limits only when the caller supplies them: the requirements require prorating by eligible working days but fix no integer rounding rule, so a partial month without explicit limits raises `InputError` instead of silently adopting a convention, while a full month uses its configured limits unchanged. A supplied prorated maximum or minimum that exceeds the configured value is rejected, because proration can only shrink a limit and must never create an obligation. No date-level placement, FastAPI route, schema, UI, PDF/Excel output or solver dependency was added.
- **2026-11-15 — Committed visits are validated on every feasibility path:** Fixed a false-FEASIBLE path in the field-visit feasibility assessment. The assessment subtracted what committed in-period visits already discharged and, when no obligation remained to place, returned FEASIBLE immediately without establishing that those committed visits formed a valid schedule. The concrete-schedule validator rejected the same input, so one question had two answers and an invalid month could be recorded as feasible. Hard-constraint evaluation now lives in one shared path used by both `validate_schedule` and `assess_feasibility`, and the assessment runs it as preflight before every return that could be FEASIBLE, including the no-remaining-obligations branch. An invalid committed schedule now yields INFEASIBLE with structured evidence naming the constraint, asset, offending dates, limit and observed value. `Evidence` gained `asset_id`, `asset_type`, `visit_date` and `offending_dates`. A committed visit to a known but inactive asset is now rejected by both paths under the new `fixed_visit_on_inactive_asset` constraint; previously it was accepted by validation and by assessment merely because the asset existed in the roster. Obligation counts now refuse boolean values, which Python would otherwise accept as integers and treat as a count of one. Fixed-visit accounting is unchanged: committed visits consume combined and area daily capacity, count once toward the per-asset monthly maximum, discharge part of their obligation, constrain placements through the seven-calendar-day interval and remain in the returned witness without duplication. Added `tests/test_fixed_visit_validation.py` with 20 tests and recorded the corrected contract in §10.8 of the requirements baseline. The three-outcome model and all approved owner policies are unchanged. No allocator, rotation, cycle-window resolution, scheduler, register generator, API, schema or UI was implemented and no solver dependency was added.
- **2026-11-15 — Validator contract hardened for the upcoming allocator:** Corrected the field-visit validator contract before any target allocator consumes it. Malformed obligation inputs are now rejected explicitly instead of being silently dropped: duplicate roster asset ids, obligation or cycle-obligation or limit-override keys naming an unknown asset, and negative or non-integer counts all raise a domain `InputError` carrying a stable constraint identifier. A positive obligation or configured positive minimum attached to an inactive asset is likewise an input error rather than a skipped entry, because skipping it reported a month as feasible while owed work was never scheduled. A malformed input is kept distinct from a well-formed but mathematically infeasible obligation set. Assessment is now defined for one calendar month: `DatePeriod` rejects a period spanning two months, which previously applied a single month's per-asset maximum to both months and hid per-asset overrun, while partial months within one calendar month remain valid and cycle obligations are resolved by the caller into the monthly portion. Added a shared `ObligationSpec` resolved once by `resolve_obligations` and consumed by both proposed-schedule validation and feasibility assessment, so the obligation-aware mode now honours explicit required counts and cycle obligations as well as configured minimums, resolving to the largest source and never treating a monthly maximum as an obligation. Added an explicit `fixed` input for visits already committed inside the month, separate from prior history: committed visits consume combined and area daily capacity, count toward the per-asset monthly maximum, discharge part of the obligation, constrain new placements through the seven-calendar-day interval, and are returned in the witness so a feasible result describes the whole month. Committed visits outside the month or off an eligible working date are reported rather than discarded. `Violation` now carries `offending_dates` (all dates involved, including every date counted by a monthly-maximum violation), `contributing_assets` with their types for daily-capacity violations, plus limit and actual values, so no caller parses message text; `conflicting_dates` remains as an alias. Added `tests/test_validator_contract.py` with 34 tests covering every correction, and recorded the enforced input contract as §10.8 of the requirements baseline. A reproducible brute-force soundness harness is kept locally under `temp/dailyworkreg/`. No allocator, weighted rotation, scheduler, generator, API, schema or UI was implemented and no solver dependency was added.
- **2026-11-15 — Date-level field-visit feasibility validator implemented:** Added the first scheduling-domain capability as pure Python under `dailyworkreg/domain/validator.py`, with tests in `tests/test_feasibility_validator.py`. It implements the hard constraints recorded in §10.1 to §10.7 and separates two operations that must not be conflated. Proposed-schedule validation is exact and reports every violation with a stable constraint identifier, the asset id and type, the conflicting dates, the expected limit and the actual value. Target-obligation feasibility assessment returns FEASIBLE only with a re-validatable witness, INFEASIBLE only on a proof (configuration contradiction, obligation above the effective maximum, failed aggregate necessary condition, an asset with no gap-respecting placement, or a completed exhaustive search), and INDETERMINATE when the declared search budget is exhausted first. The module has no FastAPI, SQLite or presentation dependency, keeps dates as date values, and is deterministic and order-independent. Tests cover all §10.6 vectors plus calendar overrides, ineligible holiday and leave dates, cross-month and cross-cycle gaps, mixed-category daily packing, per-asset minimums enforced only in obligation mode, a configured minimum above the maximum, determinism, and two soundness sweeps that cross-check verdicts and witnesses against exhaustive brute force. Added §10.7 to the requirements baseline recording the three-outcome contract, its proof conditions, the fact that greedy placement cannot establish infeasibility, and the cost boundary at which a large roster returns INDETERMINATE. No scheduler, target recommender, register generator, API, schema or UI was implemented.
- **2026-11-15 — Corrected field-visit feasibility model and deterministic test vectors:** Extended §10 of the requirements baseline with a new §10.6 recording the corrected mathematical model for field-visit feasibility. It defines the notation `W` (eligible working dates), `C` (combined daily capacity), `A`, `D`, `F` (required area, DTC and feeder visits); states the two necessary aggregate conditions `A <= 2 * W` and `A + D + F <= C * W` and labels them necessary but not sufficient; separates the area-specific daily maximum of 2 from the combined daily cap of 3; records that area, DTC and feeder visits may share a working date so category day counts must not be added without a non-overlap proof; restates the 7-calendar-day revisit interval with the `(v - 1) * 7` minimum calendar span and the rule that month and cycle boundaries do not reset the interval; explains that a per-asset monthly maximum of 3 is an upper bound and not a visit obligation; records a conditional 16-area example (48 required visits against a 46 maximum at 23 working days, hence infeasible) marked explicitly as illustrative rather than an approved target; and adds a 22-row deterministic test-vector table covering calendar-gap boundaries, weekend and cross-month/cross-cycle gaps, per-asset monthly caps, area and combined daily caps, mixed-category packing, aggregate necessary conditions, the 113-DTC quarterly cycle and its 38/38/37 allocation, and deterministic versus alternative regeneration. §16 item 1 was extended to state that these test vectors define the validation basis for the joint allocator, which remains unimplemented and unvalidated.
