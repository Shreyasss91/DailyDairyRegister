- **2026-11-19 — Turn a folder of month PDFs into the one document the office prints:** Every issued month exports as its own PDF and every one of those files ends with an issued-version identification page - the version, its standing, the fingerprint, the finalisation id and the evidence - so printing a year of registers meant nineteen pages of hashes between the register pages, and the combined print path that existed was the browser dialog over one month at a time. `dailyworkreg/interfaces/print_pdfs.py` is the second interface of the application, after the HTTP one: a command that takes the folder those PDFs were exported into as its only input, drops the last page of each file and writes what is left as a single PDF beside it. The destination is derived rather than asked for - an `after` folder next to the folder it read, which is the layout the operator already uses, and `after-merged` when the folder being read is itself named `after`, so a folder is never both the input and the output and a second run cannot merge the document into itself. Order is file-name order, which is chronological for the names this repository exports, so nothing is sorted by hand. The identification page is recognised by position, not by reading its text: `application.export` starts it on a fresh page after the final date row, so position is the contract and a month whose wording differs cannot be merged with its hashes still attached. Cycle obligations now carry integer visit counts per asset: the resolver previously built a month's obligations from a set of asset ids, so a DTC owing two visits in one month was recorded as owing one while the month total said two, and four visits were silently reduced to one rather than reported as over the monthly maximum. `verify_cycle()` is now an independent structural verifier rather than a key counter: it checks month identity and ordering against the declared cycle, month indices, roster membership, positive integer obligation values, per-month totals against their obligation sums, per-asset totals against both `cycle_totals` and `visits_per_asset`, scheduled assignments against obligations including multiplicity, and the even-distribution contract; `run_cycle()` verifies a resolution before allocating from it and fails closed under `cycle_resolution_invalid` rather than proceeding. Committed visits are now reconciled across the whole cycle: a fixed visit in any month discharges that asset's cycle obligation even when the resolver assigned a different month, so the asset is no longer allocated a second visit; commitments in months that are not selected for placement, and in months whose allocation fails, are still carried forward as history rather than forgotten; committed visits are preserved unchanged and never duplicated; and commitments exceeding the cycle obligation are reported as `cycle_obligation_over_covered` evidence instead of fabricating or silently dropping visits. The allocation seed is now effective: the asset id was the final tie-breaker, so every seed produced the same schedule, and the earlier test compared only per-asset counts, which could never differ. Placement now derives per-asset and per-date tie keys from the seeded generator and ranks assets by constraint pressure, then remaining count, then scheduling weight, then that key, so alternative seeds reach different valid arrangements while per-asset counts stay fixed. The seed still cannot outrank constraint pressure or change an obligation. Scheduling weights are passed into the allocator through `AllocationRequest.weights`, so the weight model is computed once by `DtcWeights` instead of being re-derived, and a missing weight sorts last. An explicitly empty, duplicated or out-of-cycle month selection is now rejected with `InputError` under stable identifiers rather than producing a successful-looking empty result, which previously reported the worst of no months, that is success, from a run that placed nothing; month selections and fallback sequences are processed chronologically so history is never carried backwards. Partial months fail closed in the allocator itself: `allocate_month()` resolves effective limits through the proration contract first, so a partial period without explicit limits raises `InputError` rather than silently applying full-month limits, effective limits must account for the default limits explicitly (falling back to the un-prorated configured default is rejected under `partial_month_effective_limits_incomplete`), and the original and effective configurations are kept separate. The multi-month cycle and fallback helpers now state that they support full calendar months only and reject a partial period under `partial_period_unsupported`, rather than implying arbitrary date-range support. The integer rounding rule for a prorated partial month remains undeclared and therefore still unresolved. Added `tests/test_cycle_correctness.py` with 69 tests pinning each defect, including the four-visits-against-maximum-three case resolving to `INFEASIBLE` rather than a reduced obligation, tampering detection for the verifier, cycle-wide reconciliation cases, and alternative-seed schedules that are revalidated independently. The full suite is 241 tests, all passing, with the 172 pre-existing tests unmodified; the allocator harness was extended with multiplicity, verification, reconciliation and selection checks and still holds at synthetic scale. Corrected the previously recorded test count for `tests/test_allocator.py` from 28 to 27. ### Fixed
- **2026-11-15 — Cycle-wide commitment reconciliation made independent of month order:** Fixed the remaining cycle-wide fixed-visit defect in the joint allocator. `run_cycle()` counted committed visits across the cycle for over-coverage reporting but discharged obligations only as its chronological loop reached each commitment, starting from an empty tally. A commitment in a month the loop had not reached yet was therefore invisible while an earlier month was placed. Measured: a DTC owing one visit in a three-month cycle, with the resolver assigning that visit to November and a committed visit locked in December, produced **two** visits for an asset owing one and reported no over-coverage, because the over-coverage calculation counted commitments but not generated visits. The same blindness affected the revisit gap: the November allocation could take a date within seven days of a December commitment, December then failed to place, and the cycle was reported infeasible even when another valid November date existed. Measured on a two-visit cycle with a commitment on 2 December: November accepted 30 November, December was rejected, and the cycle came out infeasible; it now places November on 2 November and the cycle is feasible. Fixed visits are now inventoried and reconciled against the whole declared cycle before any month is allocated. Each committed DTC visit consumes exactly one obligation unit — charged to the month it falls in when that month still owes a unit, otherwise to the earliest month that does — so newly allocated visits plus committed visits equal the declared obligation for every DTC, and a whole-cycle commitment count is never subtracted independently from each month, which would over-subtract an asset owing units in two months. Every committed visit outside the month being placed is supplied to the validator as a new third input category, gap blockers, which constrain the seven-calendar-day interval in both directions while consuming no capacity and no obligation in that month; a commitment is never supplied as both the month's fixed visit and a blocker, so it is never counted twice, and the allocator does not duplicate the validator's gap arithmetic. Commitments are validated wherever they fall, including months that are not selected for placement, through a new `validate_committed_visits()` that reuses the same hard-constraint path per calendar month rather than reimplementing it; a mapping for a month outside the cycle, a visit filed under a month that does not contain its date, and a commitment failing the hard constraints all raise `InputError` under stable identifiers instead of being silently accepted as a discharge. This immediately caught a defect in this repository's own test data, which had used a Saturday as a working date in an unselected month. Cycle accounting is restricted to DTC cycle members: committed area and feeder visits are preserved, consume combined and area daily capacity and constrain gaps, but are never compared with the cycle's per-visit obligation and never produce DTC over-coverage evidence. The declared `CycleResolution` is now distinguished from the effective obligations a month is allocated against (`MonthPlan.declared_obligations` versus `MonthPlan.obligations`), and the inventoried commitments are reported on `MultiMonthResult.committed_visits`. Added `tests/test_cycle_commitments.py` with 33 tests covering the duplicate-visit defect, the future-gap constraint, a different earlier date being chosen, commitments in unselected months, over-coverage preservation, area and feeder exclusion from cycle accounting, and every rejection path. The full suite is 274 tests, all passing, with all 241 preceding tests retained; the allocator harness gained a future-commitment section and the validator soundness harness is unchanged. No tri-state semantics were weakened, no unresolved case was converted into an infeasibility claim, and no scheduling or solver dependency was introduced. No draft-register generation, FastAPI route, schema, database, UI, PDF or Excel output was added.

- **2026-11-15 — Joint date-level allocator with validator-backed acceptance:** Added `dailyworkreg/domain/allocator.py`, which places a month's obligations onto eligible dates jointly across areas, DTCs and feeders. Placement is constrained-first — at each step the asset with the fewest still-viable dates is placed next — so a flexible visit cannot consume the last date a tightly constrained asset needed, which is the failure mode plain first-fit suffers. Visits are spread by preferring the least-loaded then earliest viable date.
